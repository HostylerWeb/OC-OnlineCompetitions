What this document is
---------------------
We reviewed the Online Competitions competition website and admin system and made a series of improvements. Most changes are about keeping customer data safe, making payments trustworthy, and helping the site stay fast and reliable as more people use it.

Nothing in this list changes what customers see on the surface in a big way  - it is mostly “behind the scenes” work that protects the business and prepares the platform for growth.


Payments and checkout
---------------------
• Fake payment success: The system now checks payment confirmations more strictly so someone cannot trick the site into giving away tickets without a real payment (where strict checking is enabled).

• Promo codes: When a customer uses a discount code, we now keep a clearer record of who used which code and which order it was tied to, so support and accounts can follow up more easily.

• Shop checkout: Customers can only open their own payment forms, not someone else’s.

• Checkout reliability: When tickets are assigned after a successful payment, the process is less likely to “half finish” and cause duplicate or missing tickets if something glitches.


Customer and public information
-------------------------------
• “Fill my details from my account”: That feature only loads the logged-in customer’s own details  - not someone else’s by guessing an email.

• Public list of competition entries: Search and paging were tightened so people cannot abuse the list to slow the site or hunt for private information.

• Public winners pages: Only the information meant for the public is shown (display name, prize, ticket number, etc.)  - not internal or private account fields.


Admin and staff access
----------------------
• Emergency and setup passwords: Sensitive admin setup keys are no longer exposed in a way that anyone could read from the public website files.

• Scheduled background jobs: Automated tasks (like clean-ups and draw checks) now use their own secret password, separate from “break glass” emergency login  - so one leaked password does not control everything.

• Fake requests from other websites: The admin and shop backends reject more types of cross-site requests that could otherwise change data while a staff member is logged in.

• Who can change what: Some admin actions that managers should not do were blocked on hidden URLs.

• Search in admin: Search is limited in length and time so one search cannot overload the system.

• Rate limits: Login, payments, and some public pages are throttled so attackers cannot hammer the site endlessly.


Wallet and referrals
--------------------
• Wallet transaction history: Completed wallet activity is no longer set up to disappear automatically after a short period (older setup risked losing history).

• Referral admin: Searching referral records by email is improved so it stays usable as referral volume grows.


Website speed and database (the “engine room”)
----------------------------------------------
• Faster lookups: The database is kept in sync with the intended indexes (like a book index) when the app starts, so common searches stay quick.

• Login sessions: Indexes were added so finding and clearing a user’s sessions when needed stays fast as user counts grow.

• Order records: How long old orders are kept is now configurable. By default, completed orders are kept for many years instead of being auto-deleted after three months  - better for accounts and disputes. Old failed checkout attempts can be cleaned up after a configurable period.

• Competition entry lists: The public “who entered” lists were optimized so they do less heavy work on each page load; new ticket sales store display names so the list does not always need extra lookups.

• Safety timeouts: Long-running internal reports are cut off after a sensible time limit so one report cannot stall the whole system.


Mobile app
----------
• Referral links and account-only areas: The mobile app now respects the same “you must be logged in” rules as the website for checkout, cart, and account areas, and referral links work in the app route.


Security headers
----------------
• The admin and shop sites are harder to embed inside malicious third-party pages (reduces “clickjacking” risk).


Local development (for your developers)
---------------------------------------
• Docker images for file storage in local dev were fixed so developers can run the stack on this machine without pull errors.


What your team should do before going live
-----------------------------------------
1. Review this work on the dell-laptop branch  - do not merge to main until you are satisfied.

2. Rotate any secrets that may ever have been exposed in old admin builds (setup, emergency, login, and the new separate password for automated jobs).

3. Set the new automated-job password in production and point scheduled tasks at the internal job URLs (your developer has the exact list in the technical handoff file).

4. After deploy, run the one-time database index sync (or restart the API so it runs on first request) and confirm order-retention settings match what finance/legal want.

5. Keep Redis running in production  - several protections depend on it.

6. Test a real payment in staging after these changes.
